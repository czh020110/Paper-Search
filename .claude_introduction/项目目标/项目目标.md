# 项目目标

## 总体流程目标

参加"科研场景下复杂学术查询的智能论文搜索与推荐"赛事，构建端到端学术论文智能搜索系统，实现从自然语言学术查询到高质量论文列表与引文关系图的自动化流程。当前已完成基础设施 → 参考系统研究 → 评测基线 → 查询理解 → 初检索 → 公共服务底座（S-003.5）→ 粗筛 → 中筛 → 精筛 → 滚雪球 → 结果整理的全流程闭环；后续继续补齐双模式运行、CLI 子命令和公开测试集回归锁定。

## 核心功能目标

- [x] 基础设施与配置治理：明确配置管理、API Key 管理、安全原则、缓存、日志、实验记录、结果输出目录和统一 Paper 数据模型，作为端到端流程可运行的硬前置保障：验收方式：文档中形成可指导后续实现的基础设施约定，不创建代码脚手架、不锁定最终部署方案
- [x] 参考系统研究与策略对齐：在业务模块实现前研究 PaSa-7B、SPAR、Ai2 Paper Finder、PaperQA2 等参考系统，提取可借鉴的查询分解、检索扩展、引文追踪、Agent 协作和评估策略：验收方式：将可落地策略映射到查询分解、检索扩展、筛选判定、结果展示和评估基线
- [x] 贯穿式评测基线与输出契约：在查询理解和初检索实现前建立小型 golden set、统一输出 schema、评测指标口径和实验记录方式：验收方式：明确最小评测样例、期望论文集合标注口径、F1/耗时/API 调用数/Token 成本/缓存命中率记录字段，以及 result.md + graph.json + experiment.json 输出 schema

- [x] 基于大模型的自主搜索策略迭代优化（当前先以规则驱动打底）：自主规划搜索词进行搜索；搜索结果过滤不相干、低质量论文；支持迭代式检索策略：验收方式：当前阶段支持关键词提取、中英文扩展和子查询构建；LLM 驱动的 query evolution 待后续滚雪球阶段引入
- [x] 初检索（mock backend）：从 fixtures 数据按 QueryPlan 过滤匹配论文，验证数据契约和流程可运行性：验收方式：对示例查询执行后可正常过滤和去重，契约测试和烟测通过
- [x] 初检索（真实 API）：通过 api_payload_translation 逐条调用 Semantic Scholar 与 OpenAlex API（S2 与 OA 各自独立生成搜索策略，不强制一一对应 sub_queries_for_retrieval），合并去重后形成种子文献候选池：验收方式：live backend 对示例查询执行后候选池稳定达到 74~103 篇，显著超过 30 篇下限，并完成 live 检索测试覆盖
- [x] 公共服务底座：补齐缓存系统、预算控制器、候选池状态机和结构化日志等共享能力，保证后续滚雪球与分层筛选可复用同一套公共基础设施：验收方式：共享能力被初检索、滚雪球、粗筛、中筛、精筛统一消费，并可在 experiment.json / logs 中追踪命中、预算与状态流转
- [x] 滚雪球扩展：精筛后根据 LLM 判定为高度相关的论文，通过 LLM（LLM_FAST_MODEL）提取 3-5 个新关键词做 query evolution 补召，并对高分论文展开双向引文追踪（S2/OA 引用和参考文献 API），达到收敛条件（重叠>70%/无新关键词/最大轮数/预算上限）时自动停止：验收方式：多轮滚动后自动收敛，候选池有效扩展，引文关系边记录到 graph.json 的 edges 中
- [ ] 双模式运行（fast / exhaustive）：提供低成本调试链路与完整评测链路两种运行方式：验收方式：fast 稳定执行查询理解 + 初检索 + 基础结果整理；exhaustive 可串联滚雪球、粗筛、中筛、精筛与结果整理，并将模式写入配置快照与实验记录
- [x] 论文综合排序（粗筛 + 中筛 + 精筛三级筛选）：基于论文标题、摘要及可用全文信息，对候选论文与原始查询进行细粒度相关性评估，输出经过排序的最终论文列表，区分高度相关和部分相关的结果：验收方式：粗筛三路混合打分截断（BM25+Embedding+Structure，池≤40跳过）、中筛 Reranker 重排序（DashScope/SiliconFlow，支持独立开关 RERANKER_ENABLED 和查询模式 RERANKER_QUERY_MODE）、精筛 LLM 100并发三分类判定，已输出结构化结果，F1/召回损失/耗时/成本持续记录中
- [x] 结果归纳整理：根据用户查询意图整理归纳搜索结果，结构化展示（列表 + 关系图）：验收方式：当前 mock + live 最小闭环均可输出 result.md + graph.json + experiment.json，正式版继续在完整筛选链路完成后增强相关性说明与引文关系质量
- [x] 阿斯达（AstaBench）公开评测集接入：从 HuggingFace 下载 `allenai/asta-bench` paper_finder_bench 数据集，跑完整搜索管线并计算 recall / precision / F1，与官方排行榜对比：验收方式：Web UI 提供评测按钮（📊 评测），支持 SSE 流式进度推送，单条查询失败不影响整体评测；当前仅支持 specific / metadata 类型（ground truth 为 corpus_ids），semantic 类型暂不支持
- [ ] CLI 子命令体系：将执行、评测、回放与检查能力拆分为 run / eval / replay / inspect：验收方式：CLI 提供四类子命令，并可分别完成单查询运行、golden set / 公开测试集评测、基于 run_id 的结果回放和运行快照检查
- [ ] 公开测试集回归、效率调优与提交前锁定：基于公开测试集和前期 golden set 评估 F1、端到端耗时、API 调用数、Token 成本和缓存命中情况，校准召回、筛选和输出参数：验收方式：形成可复现实验结果，提交前锁定模型、阈值、Top-K、批大小、预算策略和结果输出口径

## 实现发现

- 赛事评测指标：F1 Score 占 70%、运行效率占 20%、回复结果结构化占 10%；成本控制（API 调用次数、Token 消耗量）直接影响评测成绩
- 成绩构成：竞赛得分 60%（公开测试集 30% + 隐藏测试集 30%）+ 专家评分 40%（创新性 15%、方案落地可行性 15%、算法泛化性 10%）
- 赛事技术要求：可使用开源或商业 LLM（需注明模型及版本），鼓励使用开源模型（Qwen、DeepSeek 等）；检索后端需对接至少一种学术搜索 API（Semantic Scholar、OpenAlex、PubMed 等）；需具备合理的成本控制意识
- 参考系统：PaSa-7B（Crawler+Selector 双 Agent + RL）、SPAR（RefChain 查询分解 + 多 Agent）、Ai2 Paper Finder（多索引语义检索 + 引文追踪）、PaperQA2（全文检索 + LLM QA）
- 当前 CLI 默认 backend 已切换为 live，Web 层已迁移到 FastAPI，并通过 `/docs` 与 `/redoc` 暴露调试入口；浏览器页面与 API 调用统一走 live backend
- live backend 已形成 Semantic Scholar 顺序检索 + OpenAlex 并行检索的双源链路，并保留 mock backend 作为测试与契约验证辅助路径
- 当前 graph.json 在最小 live 闭环下已稳定输出节点结构；引文边由初检索和雪球两阶段边经 `_merge_edges` 合并去重
- 公共服务底座（S-003.5）核心模块全部就绪并测试覆盖：CacheStore 文件缓存（领域分区 + TTL）、BudgetController 硬限制（API/Token/轮数/池大小）、CandidatePool 状态机（8 状态 + 合法转换校验）、错误分类基座（ApiTimeoutError/ApiRateLimitError 等 + httpx 映射）、结构化 JSON 日志、config 三级优先级（env > config.local.json > default）；79 tests 全通过，峰值 RSS 46 MB
- 筛选链路骨架已搭建：coarse_score / rerank / judge 三个模块均已实现状态转换框架和穿透模式（当前无模型接入时自动穿透），候选池论文可完成 seed → ... → selected 的完整状态流转
- 滚雪球 LangGraph StateGraph 已编译为模块级单例缓存，四节点（query_evolution / re_search / expand_citations / check_convergence）迭代闭环骨架就绪；所有节点函数当前为桩，待后续接入 LLM 和真实 API
- OpenAlex 检索已实现 while cursor 分页循环，Semantic Scholar 和 OpenAlex 均已集成 CacheStore 缓存和基于错误分类的智能重试策略
- live_backend 已消费 api_payload_translation 参数翻译（含 CJK 字符过滤和纯字母校验），并保留 fallback 到 `_build_english_queries` 的兼容路径；S2 与 OA payload 已各自独立生成（S2 语义长句+结构化过滤，OA BM25 关键词句子+filter），不再强制一一对应 sub_queries_for_retrieval
- 查询理解已新增 LLM 路径（通过 LangChain + ChatOpenAI），规则路径补充 query_expansion_policy 输出；live 模式默认走 LLM 路径，无 LLM_API_KEY 时直接报错不静默回退，保证生产链路不因缺 key 而降级到低质量规则结果；LLM 规则路径（_build_query_plan_rules）中 S2/OA 不再共用 sub_queries，分别独立构建：S2 生成语义长句+venue/fieldsOfStudy过滤，OA 生成关键词句子（去重后的 core+methods）
- 查询理解 LLM 路径已从 `with_structured_output` 回退为裸 `invoke` + `_parse_query_plan_json`（`model_construct` 跳过验证、缺失字段 fallback 到默认值），保留了 `_parse_query_plan_json` / `_build_schema_from_partial` / `_extract_list` 三个解析函数；LLM 输出格式兼容性由 prompt 要求 + Pydantic schema 约束 + 自动补齐三重保障
- 查询理解保留了 `_parse_query_plan_json` / `_build_schema_from_partial` / `_extract_list` 三个解析补充函数，覆盖 LLM 输出字段名层级偏移、字段缺失等兼容场景；LLM 输出不满足 schema 时通过 `model_construct` 填充默认值而不是直接报错，保证生产链路可用性
